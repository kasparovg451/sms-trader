# SMSTrader — дорожная карта

> Документ о том, **куда мы идём и почему**. Не список задач, а карта.
> Задачи живут в конце файла, в разделе «Ближайшие шаги».

---

## 1. Цель

Сделать **настоящий мессенджер на C++** — не учебную поделку, а работающую программу:
сервер, клиент, база данных, графический интерфейс, сеть.

Вторая цель, которая на самом деле первая: **научиться программировать по-настоящему**.
Понимать каждую строчку, которая лежит в репозитории. Уметь объяснить, почему она такая.

Из этого следует главное правило проекта:

> **Скорость не важна. Важно понимание.**
> Лучше одна функция, которую ты понимаешь полностью, чем модуль, который «просто работает».

**Ориентир по качеству (2026-09-07): Telegram.** Реализуем проект на самом высоком уровне —
архитектурные решения, протоколы, UX тянутся к тому, как это устроено в топовом продакшн-
мессенджере, а не к минимально работающему прототипу. Это не значит копировать Telegram
буквально или гнаться за фичами раньше времени — это ориентир по *качеству инженерных решений*
на каждом этапе, согласованный с принципом «правильно, современными технологиями» ниже.

### Как мы работаем вместе

*(обновлено 2026-09-07 — формат пересмотрен по ходу проекта)*

Код в основном пишу я — включая логику, не только boilerplate. Причина смены формата:
элементарный и даже сложный код ИИ сейчас пишет быстро и хорошо, тратить время на ручной
набор синтаксиса — не лучшее вложение. Но цель проекта («понимать каждую строчку») не
отменяется — меняется только то, кто набирает код руками.

| Я делаю | Ты делаешь |
|---|---|
| Пишу код — логику и boilerplate | Читаешь, разбираешь, понимаешь написанное |
| Явно проговариваю опасные места (off-by-one, границы, деление на ноль и т.п.) | Учишься видеть такие места сам — в том числе в чужом/сгенерированном коде |
| Реализую правильно, современными средствами языка, без хаков | Указываешь, если что-то видится не так |
| Мелкие доработки (edge case'ы, полировка) явно фиксирую, но не блокирую ими прогресс | На отдельном этапе тестирования — углубляемся и доделываем |

Если код непонятен — разбираем, пока не станет понятен. Не понимать написанное — не вариант,
даже если пишу его не ты.

## 2. Где мы сейчас

**Что уже есть:**

- Консольное приложение: добавить сообщение, вывести список, счётчик, help, exit, **search**
- Разделение на модули: `command`, `message`, `datetime`, `search`, `storage`, `validation`
- Хранение в JSON через `nlohmann/json`, загрузка и сохранение, с полем `date` у сообщения
  (`std::chrono::sys_seconds`, сериализация через `std::format`/`std::chrono::parse`)
- Относительное время в духе Телеграма (`formatRelativeDate`) — «только что» / «N минут назад» /
  «сегодня» / «вчера» / «29 августа» / «29 августа 2026»
- Нечёткий поиск (`searchMessages`) — расстояние Левенштейна, токенизация по словам, порог 70%,
  топ-5 результатов по похожести
- Валидация входных данных из JSON (`isValidMessage`, `isValidCommand`, включая `date`)
- CMake + FetchContent, C++20, `/W4`, **без `<Windows.h>`** — код кроссплатформенный
- Первый тест (`command_module_test`) через `ctest`

**Этап 0 закрыт (2026-09-07).** Сборка чистая, без предупреждений, полный цикл
сохранение → JSON → загрузка проверен вручную и работает.

**Известные ограничения** (сознательно отложены до этапа тестирования/углубления, см. принцип
«правильно, но не переуглубляясь» в разделе 1):

- Поиск регистрозависим — кириллица не приводится к одному регистру (`std::tolower` для UTF-8
  ненадёжен, нужна локале-зависимая обработка)
- Даты хранятся и сравниваются в UTC, не в локальном часовом поясе пользователя

**Слабые места архитектуры**, которые мы будем лечить (это нормально, так и учатся):

| Проблема | Почему это плохо | Когда чиним |
|---|---|---|
| Глобальная `std::vector<Message> messages` через `extern` | Её может испортить кто угодно, нельзя завести два чата, невозможно тестировать | Этап 1 |
| Логика и вывод перемешаны (`addMessage` сама читает `cin`) | Не переиспользовать ни в сети, ни в GUI | Этап 1 |
| Об ошибках сообщаем через `std::cout` и `return;` | Вызывающий код не знает, что случилось | Этап 1 |
| `id = size() + 1` | После удаления сообщения id столкнутся | Этап 1 |
| Всё в одном исполняемом файле | Не получится сервер + клиент | Этап 3 |

Ни одна из этих проблем не «позорная ошибка новичка». Это **ровно те грабли, на которых
объясняют, зачем нужны классы, `std::expected`, слои и интерфейсы**. Пройдём по ним по
очереди, и каждый раз будем понимать, какую конкретную боль лечим.

### Этап 1. Ядро: нормальная архитектура

Самый важный этап для обучения. Здесь консольная поделка превращается в программу
с внятной структурой.

**Результат:** снаружи всё то же самое, но внутри — слои. Логика ничего не знает
ни про `cout`, ни про JSON.

```
   +-----------------------------+
   |  UI  (консоль)              |  читает ввод, печатает вывод
   +-----------------------------+
   |  Логика (MessageStore)      |  add / list / find / remove
   +-----------------------------+
   |  Хранилище (JsonStorage)    |  load / save
   +-----------------------------+
```

Ключевые изменения:

- `class MessageStore` вместо глобального вектора — данные и операции над ними вместе
- `addMessage(author, text)` принимает готовые строки и **возвращает** результат;
  чтение с клавиатуры уезжает в слой UI
- Интерфейс хранилища (`IStorage`) — чтобы потом подменить JSON на PostgreSQL,
  не трогая логику. Это прямая подготовка к Этапу 5
- Нормальные id: счётчик, не зависящий от размера вектора
- Ошибки — типами, а не печатью в консоль

**Что учим (большой блок теории):**

- Классы: поля, методы, конструкторы, `private`/`public`, инварианты
- RAII — почему в правильном C++ не нужен `delete`
- Ссылки против копий, `const&`, move-семантика (`std::move`) — и главное, **зачем**
- `std::optional`, `std::expected` — возврат «значение или ошибка»
- Наследование и виртуальные функции — но только там, где это оправдано
- Умные указатели: `unique_ptr`, `shared_ptr`
- Что значит «отделить интерфейс от реализации» и почему это не бюрократия

### Этап 2. Стабильность

**Результат:** программу трудно уронить. Ошибки понятны. Тесты ловят регрессии.

- Обработка ошибок целиком: битый JSON, нет файла, нет прав, диск полон
- Тесты на все модули, переезд с `assert` на нормальный фреймворк — **Catch2**
  (проще GoogleTest, отлично подходит для обучения)
- CI на GitHub Actions: каждый push собирается и прогоняется тестами
- Санитайзеры (ASan/UBSan) — они ловят выход за границы массива и утечки,
  то есть буквально показывают твои ошибки с памятью
- Логирование вместо `cout` для диагностики (`spdlog`)
- UTF-8 и русский язык в консоли Windows — отдельная больная тема, разберём честно
- Единый стиль кода: `clang-format`

**Что учим:** unit-тесты и зачем они нужны, undefined behaviour, работа с памятью,
кодировки (UTF-8 против UTF-16 против cp1251), автоматизация.

### Этап 3. Сеть: сервер + клиент

Здесь проект впервые становится **мессенджером**, а не блокнотом.

**Результат:** два процесса. Сервер держит сообщения, клиенты подключаются по TCP,
сообщение одного видят остальные.

- Репозиторий делится на `core/` (общая логика), `server/`, `client/`
- Сокеты. Библиотека: **Asio (standalone)** — стандарт де-факто и будущее `std::net`
- Свой протокол поверх TCP: как понять, где кончилось одно сообщение и началось
  следующее (framing) — классическая задача, которую все решают руками
- Многопоточность: несколько клиентов одновременно
- `std::mutex`, гонки данных, дедлоки — на живом примере, а не в теории
- **TLS** поверх сокетов (Asio SSL, через OpenSSL) — раньше стоял в Этапе 7, поднят сюда
  (решение от 2026-09-07): открытый трафик мессенджера — не тот уровень, на который
  ориентируемся. Добавляем после того, как plaintext-версия с несколькими клиентами
  и настоящим framing уже работает — не всё сразу

**Что учим:** TCP/IP, порты, сокеты, блокирующий и асинхронный ввод-вывод,
event loop, потоки, синхронизация, сериализация.

Самый сложный этап. Он же самый интересный.

### Этап 4. API и протокол

**Результат:** к серверу можно подключиться не только нашим клиентом, но и из браузера,
из Python, из чего угодно.

- HTTP-сервер поверх ядра. Библиотека: **Crow** или **Drogon**
  (выберем, когда дойдём: Crow проще, Drogon мощнее)
- REST-эндпоинты: `GET /messages`, `POST /messages`, `GET /users/{id}`
- **WebSocket** для настоящего realtime-чата — опрашивать сервер по HTTP для мессенджера плохо
- Пользователи, регистрация, вход. Пароли только хэшем (**Argon2** или bcrypt), никогда открытым текстом
- Токены сессий (JWT)
- Документация API

**Что учим:** HTTP, методы, коды ответов, REST, stateless-архитектура,
аутентификация против авторизации, основы безопасности.

### Этап 5. PostgreSQL

**Результат:** сообщения живут в базе. JSON-файлы остаются только под конфиги.

Благодаря интерфейсу `IStorage` из Этапа 1 это будет **новая реализация, а не переписывание
проекта**. Ты увидишь на практике, ради чего мы городили абстракцию.

- Схема: `users`, `chats`, `messages`, `chat_members`
- Ключи, внешние ключи, нормализация — почему не «всё в одну таблицу»
- SQL: `SELECT`, `JOIN`, `WHERE`, `ORDER BY`, `LIMIT`
- Подключение из C++: **libpqxx**
- Транзакции и ACID — что будет, если сервер упадёт на полпути
- Индексы: почему запрос по миллиону сообщений тормозит и как это чинить
- Миграции схемы
- SQL-инъекции и параметризованные запросы

**Что учим:** реляционная модель, SQL, транзакции, индексы, пул соединений.

### Этап 6. GUI

**Первый срез сделан (2026-09-08), с опережением графика** — перепрыгнули сюда сразу
после Этапа 3, минуя Этапы 4-5 (HTTP API, PostgreSQL). Причина: запрос «нормальный UI,
чтобы всё работало» перевесил строгий порядок этапов — решение осознанное, не случайное.
GUI-клиент говорит с сервером напрямую по тому же TLS+JSON протоколу, что и консольный
клиент, — HTTP/REST для этого не понадобился технически, он остаётся отдельной задачей
Этапа 4 (для интеграций извне, не для нашего же GUI).

**Что реально сделано:** `smstrader_gui` — Qt 6 Widgets, окно со списком сообщений, полем
автора, вводом текста и поиском. Сетевой слой (`NetworkClient`) живёт в фоновом потоке,
сигналы в GUI-поток идут только через явный `Qt::QueuedConnection` (см. журнал решений —
почему это обязательно, а не опционально).

**Результат:** окно с чатом. Список диалогов, история, поле ввода, отправка.

Основной вариант — **Qt 6**:

- Родной C++, значит вся логика ядра переиспользуется напрямую
- Кроссплатформенность: Windows, Linux, macOS
- Огромная экосистема и документация
- Qt Widgets (классика, проще) или QML (современнее, красивее, с анимациями) — решим на месте

**Про «гибрид»** — да, скорее всего он будет, и это нормальная взрослая архитектура:

| Вариант | Смысл |
|---|---|
| C++ ядро + Qt/QML | Всё в C++, максимум производительности |
| C++ сервер + веб-клиент на React | Чат работает в браузере, ядро остаётся на C++ |
| C++ сервер + Python-скрипты | Python для аналитики, ботов, админки — там, где C++ избыточен |

Ядро всегда остаётся на C++. Гибрид — это не «сдался», а «выбрал правильный инструмент
для конкретного слоя». Так устроены все большие проекты.

**Что учим:** событийная модель, сигналы и слоты, отделение UI от логики (MVC/MVVM),
почему нельзя ходить в сеть из UI-потока.

## 5. Принципы

1. **Работающий код на каждом шаге.** Никаких «сломано неделю, зато рефакторим».
2. **Один коммит — одна законченная мысль.** История репозитория тоже документация.
3. **Не тащим библиотеку, пока не поняли, какую боль она лечит.** Сначала боль, потом лекарство.
4. **Каждая абстракция должна оправдаться.** Если интерфейс не даёт ничего сейчас
   и не даст потом — он лишний.
5. **Тест пишется, когда есть что тестировать.** Не догма, но регрессии ловить надо.
6. **Непонятная строка — это стоп-сигнал.** Останавливаемся и разбираем.

## 7. Журнал решений

Сюда записываем важные развилки и **почему** выбрали именно так.
Через полгода это спасёт от вопроса «а зачем мы вообще это сделали».

| Дата | Решение | Почему |
|---|---|---|
| 2026-08-29 | C++20, CMake, nlohmann/json | Уже в проекте, менять нет причин |
| 2026-08-29 | Идём слоями: ядро -> сеть -> API -> БД -> GUI | Каждый слой опирается на предыдущий; так учатся, а не прыгают |
| 2026-09-07 | Смена формата: код в основном пишу я (ассистент), не пользователь | ИИ сейчас пишет элементарный и сложный код быстро и качественно; ручной набор синтаксиса — плохое вложение времени. Понимание кода остаётся обязательным — меняется только, кто набирает руками |
| 2026-09-07 | Этап 1 делаем не полностью — только минимальный `MessageStore`, без `IStorage` | `IStorage` понадобится реально только на Этапе 5 (PostgreSQL); вводить его раньше — абстракция без немедленной пользы |
| 2026-09-07 | Ориентир по качеству — Telegram, но **не** его протокол MTProto. Берём TLS + свой протокол поверх него | MTProto решает проблемы масштаба и цензуры Telegram, которых у нас нет; версия 1.0 имела реальные найденные уязвимости (не прошла публичного рецензирования до релиза). TLS — открытый, десятилетиями проверенный стандарт. Telegram — ориентир по UX и уровню инженерной дисциплины, не по копированию конкретных протокольных решений |
| 2026-09-07 | Переход на vcpkg (встроенный в Visual Studio) для OpenSSL, `vcpkg.json` + `CMakePresets.json` | OpenSSL не собирается через `FetchContent` как заголовочные библиотеки (Asio, nlohmann/json) — своя система сборки. vcpkg — стандартный современный способ на Windows. Путь к toolchain в `CMakePresets.json` жёстко привязан к этой машине (известное ограничение, не переносимо без правки) |
| 2026-09-08 | Qt-заголовки с `Q_OBJECT` кладём **рядом** с `.cpp`, не в подпапку `headers/` (как остальной проект) | Обнаружен реальный баг связки CMake 4.4.2 + Qt 6.11.1: `AUTOMOC` не находит `#include "headers/foo.h"` из подпапки, хотя `moc` вручную заголовок разбирает без проблем — воспроизведено на минимальном примере. Раз этот баг тулчейна, а не наш — обходим структурой файлов, а не костылём в коде |
| 2026-09-08 | GUI: сигналы `NetworkClient` → `MainWindow` подключаем с явным `Qt::QueuedConnection` | Фоновый поток приёма эмитит сигналы; без явного указания Qt может (в зависимости от «принадлежности» объекта потоку) выполнить слот прямо в фоновом потоке — небезопасное изменение виджетов не из GUI-потока. Баг тихий, не всегда падает сразу — лучше не полагаться на `Qt::AutoConnection` здесь |
| 2026-09-08 | Post-build копирование `platforms/qwindows(d).dll` рядом с `.exe` через `CMakeLists.txt` | Qt ищет платформенный плагин в `platforms/` рядом с исполняемым файлом; vcpkg копирует основные Qt DLL автоматически (`applocal deps`), но не плагины. Без этого — тихий "Debug Error" при старте (`no Qt platform plugin could be initialized`), выглядящий как случайный краш |
| 2026-09-08 | QSS-стили применяем через `QApplication::setStyleSheet` (в `main.cpp`), не через `QMainWindow::setStyleSheet` на конкретном окне | На Windows нужен `QApplication::setStyle(QStyleFactory::create("Fusion"))` — родной стиль игнорирует большую часть QSS. Но даже с Fusion стиль, установленный на `this` внутри `MainWindow`, не применялся визуально (кнопки оставались системными), хотя `styleSheet()` программно возвращал верную строку — подтверждено логированием. Причина не выяснена до конца, но на уровне `QApplication` стиль применяется надёжно — используем рабочий способ |
| 2026-09-08 | Для PostgreSQL используем `libpq` (чистый C API), не `libpqxx` (C++-обёртку) | `libpqxx` на Windows/vcpkg (динамическая линковка) даёт `LNK2005: уже определён в ...obj` для символов `std::basic_string_view` — известный класс проблем MSVC: DLL, экспортирующая символы с типами STL в публичном интерфейсе, конфликтует с той же инстанциацией шаблона в коде потребителя. Microsoft прямо не рекомендует передавать объекты STL через границу DLL. `libpq` — чистый C, эта проблема физически невозможна; чуть больше кода (ручное `PQclear`/`PQfinish` через RAII-обёртки), зато без сюрпризов линковки |
| 2026-09-08 | HTTP API — **Crow** (не Drogon), тянем с ветки `master`, не с зафиксированного тега | Тег `v1.2.0` использует устаревший `asio::io_service`, убранный из современного Asio (у нас 1.32) — несовместимость по времени выпуска. Заодно пришлось добавить `asio` как vcpkg-пакет (`vcpkg.json`) — `Crow` сам ищет его через `find_package`, а не через наш `FetchContent` |
| 2026-09-08 | JWT — используем `jwt-cpp/traits/nlohmann-json/defaults.h`, не голый `jwt-cpp/jwt.h` | Установленная версия `jwt-cpp` — шаблонная по JSON-библиотеке (traits), голое `jwt::create()`/`jwt::decode()` не компилируется без явного указания traits. `defaults.h` переопределяет простой API под `nlohmann::json`, который уже используется в проекте — не тащим вторую JSON-библиотеку (picojson, дефолт по умолчанию) |
| 2026-09-09 | `smstrader_http`: добавлен флаг `/bigobj` (MSVC) | После добавления WebSocket-маршрута (`crow/websocket.h`, сильно шаблонный код) компиляция `main.cpp` стала падать с `C1128: число секций превышает предел формата объектного файла`. Это лимит формата COFF на число секций в `.obj`, не наша ошибка — `/bigobj` снимает лимит, штатный флаг MSVC для таких случаев (шаблоны, генерящие много кода в одной единице трансляции) |
| 2026-09-09 | GUI: сетевой слой — `QNetworkAccessManager`/`QWebSocket` (Qt), не собственный Asio+OpenSSL, как раньше | GUI теперь ходит в HTTP API, а не в свой бинарный протокол — HTTP/WebSocket-клиент пришлось бы либо писать руками поверх Asio (парсинг HTTP-ответов, WS-рукопожатие, маскирование фреймов — заметный объём кода ради того, что Qt уже даёт из коробки), либо взять Qt-нативные классы, которые и так тянутся с `qtbase`/`qtwebsockets`. GUI и так на Qt — использовать чужой сетевой стек внутри Qt-приложения было бы искусственным ограничением. Заодно ушла ручная TLS-настройка (`asio::ssl::context`) — Qt сам работает с TLS через свой backend (собран поверх той же OpenSSL из vcpkg) |
| 2026-09-09 | GUI доверяет серверному сертификату через `QSslConfiguration::setCaCertificates({certs/server.crt})`, подключается по `localhost`, не `127.0.0.1` | Тот же принцип, что был в TCP-клиенте (Этап 3) — не `verify_none`, а явное доверие конкретному сертификату. Разница в деталях: Qt по умолчанию сверяет имя хоста из URL с сертификатом автоматически (в отличие от ручного `host_name_verification("localhost")` на Asio), поэтому подключаемся по имени, на которое сертификат реально выписан (`CN=localhost`), а не по IP |
| 2026-09-09 | Баг: белый текст в `QLineEdit` (поля ввода нечитаемы) — исправлено явным `color` в QSS | `QLineEdit { background: white; ... }` в `kStyleSheet` задавал только фон, не цвет текста. На системе с тёмной темой Windows Qt6 (с версии, где добавлена автоподдержка тёмного режима) подставляет в палитру по умолчанию белый цвет текста — получался белый текст на принудительно белом фоне: невидимо. Добавлены явные `color` для `QLineEdit`, `QLabel` и фон для `QDialog` — весь GUI теперь не зависит от системной темы, как и задумывалось изначально (см. решение от 2026-09-08 про QSS на уровне QApplication) |
| 2026-09-09 | Баг: GUI падал с `QSslSocket::connectToHostEncrypted: TLS initialization failed` / `No functional TLS backend was found` — исправлено post-build копированием плагина в `tls/` | Ровно тот же класс проблемы, что с `qwindows.dll` (см. решение от 2026-09-08): в Qt6 TLS-бэкенды (OpenSSL/Schannel/...) грузятся как плагины из подпапки `tls/` рядом с exe, а не линкуются напрямую. vcpkg копирует основные Qt DLL автоматически, но не плагины. Скопирован `qopensslbackend(d).dll` тем же `add_custom_command(POST_BUILD)`, что и платформенный плагин |
| 2026-09-09 | Тесты (Catch2): все `TEST_CASE` названы латиницей, не кириллицей | `catch_discover_tests` регистрирует каждый кейс в `ctest` как отдельный тест и запускает `smstrader_tests.exe` подпроцессом с именем кейса в argv. На Windows это ломает кириллицу в командной строке — реально воспроизведено: бинарник напрямую все 42 проверки проходил, а `ctest` показывал 0% с `No test cases matched` из-за мятой кодировки в аргументе. Комментарии и проверяемые строки внутри тестов кириллицей остаются — они через argv не проходят, ломается только то, что передаётся в командной строке |
| 2026-09-09 | Тест `searchMessages: sorted by descending similarity` переписан на другие тестовые данные | Первая версия теста сравнивала `"test"` с `"testing"` (расстояние 3, длина 7 → схожесть ≈0.57) и ожидала, что оба сообщения попадут в результат — но 0.57 ниже порога 0.7 из `search.cpp`, поэтому `"testing"` вообще не должно совпасть. Тест упал сразу после первого прогона — не баг в `search.cpp`, ошибка в тестовых данных, придуманных не глядя на формулу схожести. Заменено на `"tests"`/`"test"` (схожести 0.8 и 1.0 — оба выше порога, но по-разному) |
